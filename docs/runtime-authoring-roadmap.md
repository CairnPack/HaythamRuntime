# HaythamRuntime 手写教程总纲

编写日期：2026-10-31。用途：指导开发者亲手实现 Runtime，并作为后续新对话展开逐步教程的入口。

本文是教学路线与设计建议，不是已实现的功能清单，也不把建议类型名当成已经确定的公共契约。每章都推进正式库实现；示例模块用于观察框架行为，完成后保留框架代码。

## 1. 这套教程要把你带到哪里

像 Minecraft Mod 教程那样，从“入口在哪里、怎样注册、哪个时机执行什么”开始，每章补上一项能观察到的能力。你已有 C#
基础，需要理解的是运行环境如何组织依赖、执行、等待和释放。

最终消费者只需引用需要的模块包、接入配置与日志、请求启动、提交业务请求及请求停止。一个进程只允许一个
RuntimeHost；编译期生成清单，Runtime 自动创建和接入模块，消费者不逐个 new／AddModule。生命周期顺序、等待、工作归属和释放由
Runtime 负责。

```text
确保进程唯一 RuntimeHost，建立最小 Event 能力
  → 直接登记内置 RegisterEvent、TaskEvent
  → 读取编译期模块清单，校验描述与构造条件，自动创建模块并接好订阅
  → 锁定模块名单
  → 执行 RegisterEvent，等待订阅者提交 Registry
  → 校验合并模块 Task 与 Event 定义
  → 等待两类注册完成，锁定 Task／Event 注册结果
  → 确认实际生命周期依赖与执行计划有效
  → 加载模块
  → 启动模块
  → 接收外部输入，匹配 Task，通过本次独立 TaskEvent 信道执行
  → 请求停止，可否决
  → 等待已接纳的业务工作结束
  → 进入不可逆停止，结束持续工作
  → 反序卸载与释放
  → 已停止，或显式报告未完成的清理
```

这里借用 Mod 教程的教学方式，不照搬 Forge、Fabric 或 KJS 的具体机制。Runtime 不需要因此引入 Tick、程序集扫描、全局静态总线或固定主线程。

### 1.2 已确认规则与建议的区别

以下来自项目约束或你在引用聊天里的明确要求，后续章节应保留：

1. Runtime 可嵌入，一个进程只允许一个 RuntimeHost；CLI 与启动器各在独立进程拥有自己的实例。不引用 HC／Gebinde 业务，不接管消费者进程退出。
2. 主生命周期串行推进；事件和任务可以异步，并按各自契约决定是否并行。
3. 正式规定一模块包一模块主类，模块包之间的依赖代表初始化依赖，普通工具包无模块不进加载图。NuGet 解析版本，构建按实际目标框架／RID 已解析包关系与包到模块清单映射生成加载图；Runtime 等依赖加载成功才加载依赖方，卸载按实际成功加载顺序反序。构造工厂／DI 仍独立待定，不强制无参构造。
4. 使用 `RuntimeEvents.OnStopRequested` 和停止事件；`OnStopRequested` 继承 `CancelableLifecycleEvent`。
5. 开始判定 Stop 时，先阻止新的外部输入进入，已经触发的工作继续执行。
6. `event.Cancel()` 否决这次停止；退出否决判定后恢复输入准入。
7. 未否决时，等待已接纳的输入工作完成，再进入不可逆停止；不能提前释放资源。
8. 按实际加载顺序后进先出卸载。业务任务失败向调用方返回错误，停止仍继续；卸载失败需要显式错误和 `Hanging` 异常锁定状态。
9. 你希望亲手编写代码；后续助手负责解释、拆步骤和检查，不默认代写完整实现。
10. 采用编译期生成模块清单、运行时自动组装。无参数 RuntimeModule 是资格标记，模块自行提供静态
    Descriptor；生成器检查接口与可创建条件，不再生成描述。跨包清单导出／聚合协议必须明确，不能仅扫描当前源码就宣称覆盖 NuGet
    模块。
11. 提供类似 `runtime.Kill()` 的“断电”旁路：运行中、Stop 等待中或 Hanging 时，由调用方明确选择，跳过否决、等待与卸载，执行约定的强制终止策略；不自动从
    Stop 升级，不宣称安全卸载。具体策略接口仍待定。
12. 模块主类接入 Task 注册表、Event 注册表与内部实现。先锁定模块名单，再通过注册事件登记 Task 和 Event，最后锁定两类注册结果；两次锁定不能合并。
13. Task 定义包含触发契约、行为和返回。Runtime 接收外部输入后匹配 Task，在任务池内管理本次执行，并返回结果。任务池不等于每项任务各占一条线程。
14. `TaskEvent` 是 Runtime 自己提供并注册的一种 Event，与模块 Event 使用相同机制。每次 Task 执行都有独立 TaskEvent
    信道，内部一次性短程工作在该信道内流转。
15. 模块 Event 继承基元 Event，在 Runtime 内管理自身执行生命周期，业务由订阅者实现。Event 能组织执行、等待和完成；载入点的具体含义、基元
    Event 与派发器的分工尚未定案。
16. Runtime 先用最小 Event 能力直接登记内置 RegisterEvent、TaskEvent，再接好模块订阅。模块名单锁定后执行
    RegisterEvent，等待订阅者提交 Registry，校验合并 Task／Event 并第二次锁定，之后才加载启动。内置事件不递归依赖
    RegisterEvent 登记自己。
17. 只在实际注册的对应事件执行时，才执行对应业务初始化。模块构造、注入、登记定义本身不自动初始化业务；不要求每个模块都有初始化事件或统一强制回调。
18. 已接纳的短程 Task 及必要内部工作自然完成，外部门禁不拦截其必要内部工作。任务失败回传原调用方并解除登记，不阻断
    Stop。持续工作分开追踪，在不可逆 OnStopping 阶段结束并等待真实结束。
19. 清理按实际成功加载顺序反序进行，仅释放自己拥有的资源；全部完成到达 Stopped。清理失败保留错误并继续仍安全的清理，最终进入
    Hanging 并返回失败。

最新规则取代早期“消费者注入模块、同进程多个实例、生成器生成描述”的提案。两次锁定和统一 Event 机制保留。注册事件必须在发出前接好订阅，具体接线
API 与 Registry 提交形状仍待定。

“锁定线程”在实现上应解释为关闭外部输入准入，线程仍要执行现有工作及其异步延续。不能挂起线程或持有一把锁跨越整个 `await` 流程。

“断电”也要明确作用范围：进程唯一的 Runtime 仍不能可靠地强杀任意托管任务。建议消费者接入真正的进程终止策略，Kill
转交明确的强制终止意图；终止宿主进程会结束其中所有工作。策略缺失、失败或意外返回时须报告终止未完成，不能靠设置状态假装工作结束。Kill
不保证卸载、日志落盘或业务一致性，不属于正常停止成功路径。

## 2. 贯穿教程的例子与职责图

使用两个独立模块包／可打包项目，每包一个模块主类，以包依赖表达初始化关系。Test 内多类仅作声明练习，完整验收不采用同一模块包多个入口；项目引用等价映射尚待实现。名字可调整：

- `StorageModule`：拥有一个可打开、可释放的存储资源，提供存储能力。
- `InstallModule`：依赖存储能力，接收安装请求，执行若干步骤并发布进度。

资源可以先用简单对象模拟。后面添加异步步骤、必要子任务和一个持续观察循环，用同一套正式框架验证行为；不引入真实下载与安装算法。

| 教学中的角色        | 对应职责                                                 | 应该隐藏在内部的复杂性                   |
|---------------------|----------------------------------------------------------|------------------------------------------|
| 消费者入口          | 声明模块、配置、日志和业务意图                           | 拓扑排序、逐模块启停                     |
| 模块主类            | 接入注册事件，在对应阶段登记 Task 和 Event，连接内部实现 | Runtime 注册与执行协调细节               |

| Event 机制          | 组织 Event 的执行、等待和完成，订阅者实现业务            | 参与名单、生命周期、顺序、完成与错误收集 |
| Task 定义与任务池   | 按触发契约选取行为，管理每次实际执行及返回               | 输入匹配、准入、调度及执行归属           |
| 每次 TaskEvent 信道 | 承载本次 Task 的内部短程工作                             | 本次执行状态、取消、结果及必要工作追踪   |

公开接口应保持小：调用方不用知道每个内部协调类型。内部先按明确职责拆开，有变化需求时再引入接口，不为了目录整齐给每个类配一个接口。

### 2.1 Task 定义、一次执行与 Event 的关系

```text
模块主类
  ├─ 订阅注册事件 → Task 注册表：收到什么输入、执行什么、返回什么
  ├─ 订阅注册事件 → Event 注册表：事件生命周期与载入点
  └─ 内部实现：由事件订阅者调用的业务代码

Runtime 在引导阶段已登记 TaskEvent（与模块 Event 使用相同机制）
外部下载输入 → 匹配下载 Task → 任务池登记本次执行
  → 建立本次 TaskEvent 信道 → 内部短程工作 → 等待完成 → 返回结果
```

同一个下载 Task 定义可以执行多次；每次都有自己的信道、执行状态、取消状态和结果。两个信道的数据分开，并不自动避免它们同时写入同一个文件，需要业务层另行协调共享资源。

这里的 Task 是领域中的任务定义或执行，不等同于 `System.Threading.Tasks.Task`。后者可以用于等待异步完成；具体代码类型叫什么，在接口设计时确定。

### 2.2 类型、事件、状态不要混为一谈

- `RuntimeState` 表示 Runtime 现在处于什么状态。
- `RuntimeEvents.OnStarting` 或 `OnStart` 这样的事件表示“此刻执行哪些挂载逻辑”，具体命名待第 5 章统一。
- 模块状态表示某模块是否已经加载、就绪、停止或失败。
- 任务状态表示某次业务工作是否真正完成。

派发一个“已启动”通知不会自动使实例就绪。只有生命周期驱动器完成启动条件检查，才能修改 Runtime 状态。对外的业务发布入口不能允许消费者伪造生命周期推进。

### 2.3 已确认的运行、停止与 Kill 流程

下面是语义流程，方法名和底层回传／回收时序仍需设计。

```text
外部输入 → 匹配已注册 Task，并检查准入
  → 建立本次执行记录，纳入 Runtime 任务池
  → 建立本次专属 TaskEvent 信道
  → 按已注册触发与行为规则执行订阅者
  → 内部短程工作在信道内按 Event 契约执行与等待
  → 必要工作实际结束 → 成功／失败／已取消
  → 返回调用方、完成在途登记并回收本次信道

调用方请求 Stop → 关闭新外部输入准入，已接纳执行继续
  → OnStopRequested
      ├─ 否决 → 返回被否决，恢复准入
      └─ 未否决 → 保持关闭，等待已接纳 Task 及必要内部工作自然结束
          → 不可逆 OnStopping
          → 结束受托管持续工作，等待其真实结束
          → 按实际成功加载顺序反序卸载，释放自有资源
              ├─ 全部完成 → Stopped
              └─ 清理失败 → 保留错误，继续仍安全的清理 → Hanging，返回失败

运行中／Stop 等待中／Hanging
  → 调用方明确选择 Kill
  → 跳过否决、等待、卸载 → 执行约定的强制终止策略
```

同一 Task 定义可以同时产生 A、B 两个独立信道和结果。信道隔离不自动解决共享文件竞争。Task 失败仍向原调用方回传并解除登记，不阻断
Stop；持续工作不能在发送停止信号前被当作普通短程 Task 等待。

`OnStopRequested` 处理器自身抛异常的处理仍待定，不与业务 Task 失败混为一谈。Kill 不自动升级，也不表示安全卸载；终止宿主进程会结束其中所有工作。

## 3. 教学路线与里程碑

最新实施顺序从 Runtime 外壳开始：先写实例状态并明确入口完成条件，再逐章填入模块、Event、注册流程、TaskEvent
与正常收尾。启动／运行／结束是生命周期大阶段，不是要求一条专用线程经历三个状态。第一章不实现完整 Stop，也不通过假成功的 Start
跳过尚未实现的初始化。

里程碑 A：第 1～5 章完成，正式框架能够按依赖启动两个模块。此时做第一次 AOT 冒烟验证。

里程碑 B：第 6～8 章完成，框架能够承载有结果、进度、子任务和持续工作的业务。

里程碑 C：第 9～10 章完成，能证明否决后继续运行、获准后安全收尾及失败可观察。

里程碑 D：第 11～12 章完成，能扩展阶段并用验证约束后续演进。

## 4. 各章展开提纲

### 第 1 章：建立 Runtime 状态与生命周期外壳

**本章目标**：先建立持有自身状态的运行实例，明确启动与结束入口的完成条件，为后续模块、Event 和任务接入提供位置。

**前置**：阅读本总纲、开发约束、当前源码及用户已有 `runtime-entry-notes.md`
，保留已完成的项目引用与消费者草图。详细手写步骤见[第一章](tutorials/01-consumer-entry.md)。

**亲手完成**：

1. 区分 Runtime 状态与物理线程，把启动、运行、结束画成三个大阶段；同时保留尚未启动、已经结束的含义。
2. 沿用已完成的 RuntimeState.cs：Created、Starting、Running、Stopping、Stopped；Stopping 专指不可逆阶段，停止判定、排空与失败后续细化。
3. 沿用 RuntimeHost.cs 状态外壳；当前公开构造尚未限制进程唯一性，后续接唯一入口时收紧，不添加假成功 Start／Stop。
4. 在已有笔记后补入口表：创建、启动、输入、停止、Kill 各由谁调用、何时完成、返回什么。状态只由内部生命周期协调逻辑推进，业务订阅者不直接改状态。
5. 将内置事件引导、自动组装、两次锁定和实际事件初始化放入启动完成条件；自然排空、持续工作结束和反序卸载放入结束条件。入口方法名待定。
6. 保留用户草图，之后通过唯一入口验证初始状态；同进程重复／并发请求不能产生第二实例，独立进程各有实例。当前 Program
   运行不证明这些目标已通过。

**产物**：RuntimeState、Runtime 实例外壳、初始状态检查，以及已有笔记中的入口与阶段规则。模块草稿接到第二章继续使用，不重复抄写。

**验收**：初始状态正确，对外不能任意写状态；能解释何时才能进入 Running／Stopped，以及当前尚未实现哪些推进条件。

**展开时重点解释**：启动完成不等于应用整个运行期结束；结束 Runtime 不等于结束某条专用线程。相应功能首次实现时就补失败传播、工作归属和清理责任，不将错误处理全部拖到最后。

### 第 2 章：声明模块并生成自动接入清单

**本章目标**：模块作者维护静态描述并标注资格；框架通过生成清单自动接入，消费者无需逐个创建或登记模块。

详细步骤见[第二章](tutorials/02-module-entry.md)。前置是第一章状态外壳与进程唯一性约束，继续保留用户笔记和源码。当前最小生成器已完成，下一步从第二章第 6 节 A 开始：定义 Runtime 公共 ModuleFactory／ModuleDefinition，再修改清单输出，接描述准备计划与唯一宿主入口。跨包导出、还原图及真实事件启动分别验证，不把对象创建冒烟视为完整加载。

**亲手完成**：

1. 沿用 static abstract Descriptor 和 SemVersion 描述；一模块包一模块主类，包依赖代表初始化依赖，不重复手写 ModuleDependency 图。现有依赖字段保留为待用户调整的旧草稿。
2. 将 RuntimeModuleAttribute 改为无参数资格标记；合法主类必须同时标记并满足接口，生成器检查类型资格。
3. 手写教学模块的静态描述，在独立 Generators 项目中逐步实现标注发现、诊断、模块清单与创建代码。
4. 定义包到模块清单映射与聚合协议，并由 MSBuild 向生成器提供实际目标框架／RID 的已解析包关系。常规符号扫描拿不到完整 NuGet 还原图，输入机制和项目引用映射均未实现。不通过 partial 生成描述。
5. 设计 Runtime 自动组装与唯一入口；描述、创建规则、模块实例配对，构造依赖来自明确的工厂或配置，不猜参数。
6. 记录 RegisterEvent 发出前如何接好订阅；实际执行在第三、四章接通。本章不以空方法伪装成功注册或启动。

**产物**：静态模块描述、无参数标记、最小生成器清单、自动组装与唯一入口设计，以及两个教学模块。

**验收**：合法模块进入清单，非法标记得到诊断；未标记不能接入；描述身份冲突明确失败；跨包清单按已实现协议聚合；同进程不创建第二个 RuntimeHost，独立进程各有实例。未实现的契约不能预填通过。

**展开时重点解释**：包依赖、模块生命周期依赖、构造能力来源分别是什么；static abstract 不保证描述深不可变。生成器与 AOT 边界见[模块清单与 NativeAOT](module-entry-aot.md)。
### 第 3 章：建立 Event 的最小执行机制

**本章目标**：Event 能组织订阅者执行、等待必要工作并完成，为下一章的注册事件提供基础。

**前置**：第 2 章的模块归属与接线方案。

**亲手完成**：

1. 定义最小基元 Event，模块 Event 从它继承。先写出事件自身的触发、执行、等待、完成与失败过程，不把它缩成状态通知。
2. 确定订阅者的异步处理器形状，优先类型化绑定；用 `System.Threading.Tasks.Task` 或 `ValueTask` 表示异步完成，不与领域 Task
   定义混淆。
3. 记录处理器所属模块，为每次事件执行确定参与者和执行数据；处理器尚未结束，事件不能报告完成。
4. 用一个明确串行的教学 Event 跑通最小执行路径。是否允许其他 Event 并行，由其契约决定。
5. 写下 Event 的“载入点”待解决的问题：它在什么时机接入、谁触发、需要哪些上下文。不要在含义未定前擅自把它等同于某个状态通知或线程入口。
6. 明确注册事件所需的基础执行机制必须先可用；Runtime 直接引导登记 RegisterEvent、TaskEvent，不能等模块完成登记后才获得基础能力。具体 API 在第 4 章定案。

**产物**：最小 Event 执行机制、订阅者归属和一次完整执行示例。

**验收**：订阅者业务得到执行；异步工作未结束时 Event 未完成；错误可观察；同一 Runtime 的两次 Event 派发执行数据不混用。

**展开时重点解释**：Event 管理执行过程，订阅者实现业务。基元 Event、事件对象与派发器如何分工尚待设计，不把所有逻辑硬塞进基类，也不预先建立庞大事件继承树。

### 第 4 章：通过注册事件建立 Task／Event 注册结果

**本章目标**：完成两次锁定之间的注册过程，再为加载生成完整依赖计划。

**前置**：第 2 章模块名单、第 3 章可执行的 Event 机制。

**亲手完成**：

1. 由 Runtime 直接登记内置 RegisterEvent 和 TaskEvent；自动组装模块并在发出 RegisterEvent 前确认订阅者已接线，再锁定模块名单。RegisterEvent
   仍是统一 Event，bootstrap 登记不递归依赖自身。
2. 模块订阅者分别登记 Task 定义（触发契约、行为、返回）和 Event 定义（生命周期与载入点）。此时登记业务，不执行下载、安装等业务。
3. RegisterEvent 订阅者提交 Registry，Runtime 校验合并模块 Task／Event；Runtime 自己的 TaskEvent 已在引导阶段登记，与模块
   Event 使用同一机制，不能偷建另一套执行系统。
4. 等待两类注册所需工作完成，校验身份与冲突，再锁定 Task／Event 注册结果。注册失败不进入运行；部分注册失败如何丢弃或回收在本章规定。
5. 校验构建导出的模块加载图，拒绝清单遗漏、重复身份、一包多主类、无效映射和环。构造依赖在创建对象前解决；业务加载按图等待依赖成功，NuGet 不执行生命周期。
6. 区分加载计划与实际成功加载记录，正常卸载依据实际记录反序执行。公开入口和内部生成清单分别包住哪些步骤，要依据等待条件定案，不能仅按名称推断。

**产物**：注册事件、两个注册表、第二次锁定及依赖执行计划。

**验收**：模块名单锁定后不能加模块，但其订阅者仍能在注册阶段登记 Task／Event；第二次锁定后不能改定义；注册处理器未完成时不能提前锁表；错误不会产生可运行的半注册实例。

**展开时重点解释**：模块自动组装、注册订阅接线、登记 Task／Event、运行这些定义是四件事。Runtime 自有事件也有明确登记与就绪过程，不依赖全局静态表。

### 第 5 章：接通加载、启动与运行

**本章目标**：获得第一个完整的正式 Runtime 启动流程。

**前置**：前四章。

**亲手完成**：

1. 在第 1 章状态外壳上接入第 2～4 章的“模块名单锁定 → 注册事件 → Task／Event 注册结果锁定”，再接加载、启动、运行。补齐阶段细节与失败记录，不能用
   Created 直接跳过注册完成条件。
2. 驱动器按计划执行所有模块的加载阶段，再进入启动阶段；进入下一主阶段前等待上一阶段必需工作完成。
3. 记录每个模块的加载与就绪状态。只有达到本阶段约定的依赖状态，依赖方才能使用对应能力。
4. 只在启动成功后开放普通业务入口；加载失败或启动失败不能落入 `Running`。
5. 从第一次取得资源起记录清理责任。模块加载一半失败时，当前模块清理自己已经取得的局部资源；Runtime 回收此前成功加载模块的资源。第
   10 章再统一完善清理协议。
6. 约束重复或并发启动，确保只有一个生命周期推进者。不要持锁等待用户处理器。
7. 接入消费者提供的日志，关联实例、模块和阶段；同时向调用方返回真实失败。
8. 以最小 Event 机制实现加载、启动挂载点，具体事件名在本章统一。RuntimeEvents
   可以作为类型命名容器，不能保存静态可变订阅；阶段执行只选择对应模块的参与者，避免遍历模块时反复广播所有处理器。
9. 对应业务初始化只由实际注册的对应事件执行。没有登记该初始化行为的模块，不因构造、注入或推进阶段而被调用一个假定存在的初始化方法。

**产物**：能启动两个依赖模块的 Runtime、失败回收路径和消费者演示。

**验收**：教学模块实际登记相应处理器后，观察到 Storage 加载、Install 加载、Storage 启动、Install
启动，随后整体进入运行；没有登记的初始化行为不会被凭空调用。任一已登记初始化失败时，消费者收到错误且已拥有资源得到处理。

**展开时重点解释**：阶段完成条件与状态转换权。此时先做一次 NativeAOT 发布和运行，尽早发现注册及调用路径中的问题，命令参考第
12 章。

### 第 6 章：让 Task 通过 TaskEvent 执行

**本章目标**：外部输入能够找到已注册 Task，通过 Runtime 自己注册的 TaskEvent 执行业务并返回结果。

**前置**：第 3 章 Event 机制、第 4 章注册结果与第 5 章可运行实例。

不再为请求另建一套脱离 Event 的执行系统。输入与结果可以有类型化的数据契约，但下载、纳入、修复、清理等操作都是已注册
Task，其执行通过 TaskEvent。以下是职责划分，不是要求创建全部候选类型的继承树。

| 定义／用途         | 负责什么                       | 参与者与执行                          | 完成和结果                           |
|--------------------|--------------------------------|---------------------------------------|--------------------------------------|
| 基元 Event         | 提供统一事件基础               | 模块 Event 从它继承；具体分工待定     | 在 Runtime 内组织执行生命周期        |
| Task 定义          | 描述触发、行为、返回           | 模块在 Task 注册阶段接入              | 不是某次执行的可变状态               |
| TaskEvent          | Runtime 自己提供并注册的 Event | 通过相同 Event 机制组织本次 Task 业务 | 等待本次必要工作，产生明确终态与结果 |
| 模块 Event         | 模块声明的执行过程与载入点     | 订阅者编写业务，可依契约串行或并行    | 按自身生命周期等待、完成或失败       |
| 生命周期与停止事件 | 加载、启动或停止判定           | Runtime 按阶段选择参与者              | 保留停止否决、等待及清理语义         |
| 进度通知           | Event 的一种用途               | 可有多个观察者                        | 不因增加观察者而重新执行 Task        |

**亲手完成**：

1. 取一个已注册的下载 Task，写清收到什么外部输入、匹配哪个定义、执行哪些订阅者业务以及返回什么结果。
2. 匹配已注册 Task 并检查准入后，建立本次执行记录纳入任务池，建立独立 TaskEvent
   信道；按注册规则执行订阅者及内部短程工作，等必要工作实际结束后返回成功／失败／已取消结果，完成在途登记并回收信道。此处不预先锁死回传与回收的底层时序。
3. 明确未匹配 Task、触发冲突、业务失败和内部故障的结果。每个请求有明确执行责任，不能任取第一个订阅者返回值，也不能把多个进度观察者当成多个业务执行者。
4. 将三种“取消”分开：生命周期否决、任务协作取消、停止后续传播。没有传播截断需求就先不提供 `StopPropagation()`。
5. 定义订阅名单与退订效果：建议单次派发使用快照；退订只影响后续派发，不代表当前处理器已经结束。
6. 如果允许通知观察者并行，先要求载荷不可变或隔离，再等待全部必要观察者，保留所有相关错误。

**产物**：通过 TaskEvent 执行的下载示例、输入匹配与结果返回规则，以及 Event 执行契约表。

**验收**：从外部输入到业务结果全程可追踪；TaskEvent 与模块 Event 走同一机制；新增进度观察者不会使下载执行两次；失败不会被悄悄当成成功。

**展开时重点解释**：生命周期事件也使用事件执行能力，但其推进权和失败策略归生命周期驱动器。不要把排序、投票和清理都写死到通用基类中。

### 第 7 章：隔离每次 TaskEvent 信道与内部工作

**本章目标**：同一 Task 定义执行多次时，各自的数据不混用，并能判断每次内部工作是否全部结束。

**前置**：第 6 章通过 TaskEvent 执行的业务。

**亲手完成**：

1. 每次 Task 执行建立独立 TaskEvent 信道，记录实例、模块、本次执行身份、输入、取消状态和结果。TaskEvent 类型／定义可复用，这些可变执行数据不可复用。
2. 本次内部一次性短程工作都在该信道内流转并保留归属。订阅者可以直接等待必要工作，或登记到本次执行作用域；作用域是同一信道的追踪手段，不是另一套任务执行系统。
3. 设计作用域关闭与子任务登记的同步规则，避免刚判定完成又登记进来一个子任务。
4. 将父处理器返回与父任务完成分开：必需子任务尚未结束时，父作用域不能完成。
5. 成功、失败或取消都必须结束在途登记；取消令牌置位不等于工作已经结束。
6. 必要内部派发延续本次信道与归属，不能偷偷变成另一个外部根任务或未追踪后台工作。多个独立外部输入各有自己的执行信道；具体子工作调用接口在本章确定。
7. 先不引入复杂线程调度器。若加入并发上限，必须避免父任务占着唯一名额等待无法启动的子任务。

**产物**：每次 TaskEvent 信道的隔离、必要工作追踪、结果与取消完成规则。

**验收**：同时运行两个下载，暂停或取消其中一个，另一个的状态与结果不受污染；卡住必要子工作时本次 Task
不能提前完成；失败到达正确调用方，结束后登记归零。共享文件写入竞争单独验证，不能靠信道隔离自动解决。

**展开时重点解释**：`async`、线程、工作身份和生命周期归属是不同概念。作用域不是任意开放的“跳过门禁”标志，其创建与延续应由框架控制。

### 第 8 章：托管持续工作，区分就绪与结束

**本章目标**：监测循环和队列消费者能够常驻，又不阻止启动完成。

**前置**：第 7 章工作归属。

**亲手完成**：

1. 给持续工作指定所属模块，暴露启动就绪、运行失败和最终完成三个可观察结果。
2. 启动阶段等待就绪信号，不等待整个循环结束；启动失败不能伪装成已就绪。
3. 将持续工作登记到模块或 Runtime 生命周期作用域，而不是某次普通业务请求中。
4. 区分普通在途业务工作与持续工作。否则停止流程会在发送停止信号前等待永不结束的循环。
5. 明确持续工作怎样停止产生新的根业务工作；停止已获准后不能不断制造新请求拖延排空。
6. 设计协作停止与完成观察：进入不可逆停止后发出结束信号，等待循环实际结束，再释放资源。
7. 持续工作意外失败须有观察通道，并定义受影响能力是否仍可调用；整体故障策略需单独记录。

**产物**：受托管持续工作的登记与状态，以及一个可控的教学循环。

**验收**：循环保持运行时 Runtime 已进入运行；就绪前失败导致启动失败；运行中失败能被消费者观察；结束信号发出后仍等待真实结束。

**展开时重点解释**：这一章先验证持续工作的独立启动与结束机制，第 9 章再由 Runtime 停止流程统一驱动。无限循环不可作为普通在途请求参与第一轮排空。

### 第 9 章：实现 Stop 请求、准入与不可逆停止

**本章目标**：实现你已经说明的停止语义，复用已有状态、事件、工作归属和模块信息。

**前置**：第 5～8 章。

**目标流程**：

```text
Running
  → 原子关闭外部新工作准入，进入 Stop 判定
  → RuntimeEvents.OnStopRequested
      → 任一否决：结束判定，恢复 Running 和准入
      → 判定处理器自身异常：策略待定，不在此默认恢复或继续停止
      → 无否决：保持准入关闭，等待已接纳的业务作用域完成
          → RuntimeEvents.OnStopping
          → 通知持续工作结束，并等待其真实完成
          → 按实际成功加载顺序反序卸载并释放自有资源
              → 全部完成：Stopped
              → 清理失败：保留错误，继续安全清理，Hanging 并返回失败
```

**亲手完成**：

1. 完成 `CancelableLifecycleEvent` 的单次派发状态与 `OnStopRequested`，每次停止请求使用新的事件实例。
2. 将检查准入与登记根执行做成一个原子操作；Stop 关闭门禁与业务请求进入之间有确定的先后。
3. 拒绝新的外部根工作；已接纳作用域的必要子工作仍可继续。生命周期控制调用也有受控的内部执行路径。
4. 等待判定处理器按契约结束，再决定恢复准入或排空。`Cancel()` 本身不负责打开门禁，也不强行杀掉处理器。
5. 未否决时等待已接纳短程 Task 及必要内部工作自然完成；这是已确认规则，不因提出 Stop 自动取消全部业务任务，外部门禁也不阻断其必要内部工作。
6. 业务任务失败仍返回原调用方，并完成在途登记，停止可以继续；Stop 的结果如何附带诊断摘要另行约定。
7. 进入 `OnStopping` 后不可再通过 Stop 否决恢复运行；让持续工作实际结束，才能进入资源卸载。
8. 定义并发 Stop、停止过程中再次 Start、处理器内部等待 Stop 的行为。建议并发外部 Stop 共享操作；正在被排空的作用域不允许同步等待自己的
   Stop 完成，可拒绝或提供不等待的请求方式。
9. 为 `Kill()` 保留不依赖 Stop 完成的控制路径：可以越过否决和排空，不等待可能卡住的处理器；消费者必须明确选择强制终止，Stop
   失败不能自行升级为 Kill。

**产物**：停止入口、准入控制、停止请求结果，以及不可逆阶段协调。

**验收**：第一次否决后仍能执行请求；第二次接受后新请求被拒绝，已有请求及其必要子工作完成后才进入 `OnStopping`；并发停止不会卸载两次。

**展开时重点解释**：否决阶段中仍要允许已接纳工作完成。持续工作产生新请求、内部后代工作和生命周期控制操作不能通过同一个无约束的
bypass 开关处理。

### 第 10 章：反序卸载、启动回滚和 Hanging

**本章目标**：只有真正处理完工作与资源，才报告停止完成。

**前置**：第 5 章的初步失败回收、第 9 章的停止协调。

**亲手完成**：

1. 以实际成功加载顺序为主，反向执行模块卸载；记录加载过程中更细的资源清理义务，处理部分初始化失败。
2. 区分卸载挂载点、资源释放和卸载完成通知，避免同一资源在多个路径里重复释放。
3. 对每项清理记录尝试与结果；重复停止或失败收尾不能无意间重做有副作用的清理。
4. 启动失败时保留原始启动错误，同时按已有义务回收；不能因为没有进入运行就漏掉资源。
5. 清理失败时继续其他仍安全的义务，并收集后续错误；如果使用方仍在使用提供方资源，就不能机械地释放提供方。
6. 只有工作结束且应释放的资源都成功释放，才到达 `Stopped`。卸载失败按已确认规则进入 `Hanging`，保持普通执行入口关闭。
7. 明确 `Hanging` 暴露的状态与诊断，并保留 `Kill()` 入口。进程强制退出由消费者决定；建议通过消费者显式提供的终止策略执行，Runtime
   不默认自行退出进程。终止策略失败或未完成终止时保留真实故障状态，不报告成功清理。

`OnStopping` 处理器失败时也不能恢复 `Running`
：保留错误，继续仍安全的停止与清理。展开本章时应明确“已清理但停止挂载点失败”和“仍有未完成清理”怎样分别返回；后者不能报告成功，卸载失败按上述规则进入
`Hanging`。

**产物**：正常卸载、初始化失败回收、错误汇总与异常锁定结果。

**验收**：Install 先于 Storage 卸载；借用方不释放 Storage 所有的资源；资源释放异常不会返回成功；启动原始错误与清理错误均可观察。

**展开时重点解释**：未响应取消的工作、等待超时和资源释放失败不是同一件事。超时不证明安全结束；若工作仍运行，保持资源有效并报告实际情况，具体超时状态与对外结果另行定案。

### 第 11 章：按照契约增加一个生命周期阶段

**本章目标**：以后可以独立增加阶段，而不只是给枚举加一项。

**前置**：前十章形成完整生命周期。

以“在启动前增加配置校验阶段”为教学练习。`Validating`、`OnValidate` 只是候选；先判断它是否值得成为独立阶段，还是现有加载阶段的一个处理器就够了。

**亲手完成的阶段设计卡**：

1. **目的**：这一阶段提供什么新的完成保证？为什么现有挂载点不足以表达？
2. **位置**：前置状态、成功后继、失败路径是什么？运行中能否进入？
3. **参与者**：哪些模块必须参加？无处理器的模块怎样通过？模块依赖要求哪个就绪级别？
4. **事件类型**：通知、执行阶段还是可否决请求？谁有权触发？
5. **完成条件**：等待哪些处理器与登记工作？持续工作需要就绪还是结束？
6. **可逆边界**：能否否决？`CancellationToken` 只取消等待还是请求阶段工作停止？
7. **资源义务**：本阶段是否获得资源？中途失败由谁清理？
8. **调用协调**：重复请求、并发请求和重入怎样处理？
9. **可观察性**：状态、结果、错误与日志怎样向调用方暴露？
10. **验证与文档**：补成功、失败、必要等待以及错误恢复场景，更新生命周期草稿。

**产物**：一张阶段设计卡、相应驱动器路径、事件定义与验证场景。

**验收**：只通过公开启动入口就能观察新阶段的顺序和失败行为；阶段失败时不会悄悄进入后续启动。

**展开时重点解释**：第一版可用显式状态机方法组织阶段。不必为了“以后扩展”立刻制造允许任意插入阶段的公共插件引擎。只有消费者确实需要注册自定义阶段时，再设计排序与兼容契约。

### 第 12 章：把完成标准变成可重复验证

**本章目标**：以后增加事件或阶段时，能发现破坏旧生命周期的改动。

**前置**：每章都保留其验收场景，本章汇总并补齐。

| 场景                                   | 应证明的行为                                                               |
|----------------------------------------|----------------------------------------------------------------------------|
| 反向注册两个有依赖的模块               | 加载顺序仍正确，卸载与实际加载相反                                         |
| 重复、缺失、自依赖、依赖环             | 在初始化副作用之前明确失败                                                 |
| 模块名单已锁定、注册事件尚在执行       | 拒绝新增模块，允许已接入模块登记 Task／Event；未完成前不锁定注册结果       |
| Task／Event 注册失败或锁定后修改       | 注册失败不进入运行；结果锁定后拒绝修改定义                                 |
| Runtime TaskEvent 与模块 Event         | 使用相同 Event 执行机制，业务由订阅者完成                                  |
| 同一 Task 同时执行两次                 | 独立信道内的数据、取消和结果不混用，内部短程工作保留本次归属               |
| 异步阶段处理器被暂停                   | 后一阶段不会提前开始                                                       |
| 父处理器已返回、必要子任务未完成       | 根执行仍未完成                                                             |
| 加载一半失败、启动中途失败             | 不进入运行；已有清理责任得到处理                                           |
| Stop 被否决                            | 不取消已有业务、不卸载，判定结束后恢复准入                                 |
| Stop 与新请求同时到达                  | 请求要么被登记并被等待，要么明确拒绝，无漏记                               |
| Stop 获准但旧请求未完成                | 不进入卸载，必要内部子工作仍能继续                                         |
| 请求失败后继续 Stop                    | 原调用方得到错误，在途登记解除，停止继续                                   |
| 持续工作启动或运行失败                 | 就绪和健康状态真实，错误可观察                                             |
| 并发 Stop、重复 Start、处理器重入 Stop | 不重复驱动、不形成自等待死锁                                               |
| 请求增加观察者                         | 业务负责者只执行一次                                                       |
| 订阅解除与正在执行的处理器             | 不把退订视为工作完成                                                       |
| 卸载或资源释放失败                     | 保留错误，正常执行锁定，不谎报已停止                                       |
| 明确调用 Kill、策略缺失或失败          | 跳过 Stop 否决和等待；不把未终止伪装成已停止；真实进程终止在专用子进程验证 |
| 同进程重复／并发创建                   | 不产生第二个 RuntimeHost，具体重复调用结果按已定政策验证                   |
| 两个独立进程                           | 各自拥有自己的 RuntimeHost，模块、订阅、状态、任务和停止互不影响           |

**验证方法**：先在现有 `src/Test/Program.cs`
写可控场景与失败检查；复杂生命周期逐渐稳定后，再决定引入正式测试框架。用完成信号或屏障控制先后，不靠固定延时猜执行顺序。关键判断失败应抛出异常或返回非零退出码，不能只打印一句“看起来正确”。

仓库规定的基础命令：

```shell
dotnet --version
dotnet build HaythamRuntime.slnx --nologo
dotnet test HaythamRuntime.slnx --nologo
dotnet run --project src/Test/Test.csproj
```

检查构建无警告。记录实际执行命令与覆盖的场景；未建立正式测试前，明确说明 `dotnet test` 没有生命周期测试可运行。

以 Windows x64 消费者为例，实际 NativeAOT 验证可从下面的发布命令开始，目标平台不同时更换 RID：

```shell
dotnet publish src/Test/Test.csproj -c Release -r win-x64 --self-contained true -p:PublishAot=true -p:TreatWarningsAsErrors=true -o artifacts/aot-smoke
```

还必须运行生成的 `artifacts/aot-smoke/Test.exe`，覆盖模块注册、事件派发、启动、实际业务与清理。先确认 Test 已引用 Runtime
并执行这些路径；发布 Hello World 不能证明 Runtime 的 AOT 兼容性。原生编译工具缺失时记录环境阻碍，不关闭分析器绕过。

记录 SDK、依赖版本、RID、发布警告与运行结果，不提交 `bin/`、`obj/` 或发布产物。第一轮 AOT 在里程碑 A
执行；引入新依赖、新事件调用方式或完整停止流程后再补相应覆盖。
