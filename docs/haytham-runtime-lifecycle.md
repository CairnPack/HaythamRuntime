# HaythamRuntime 的分层职责与生命周期需求草稿

状态：需求草稿。事件框架已经按 [Event 框架规格](event-framework.md) 实现，具体接口和规则以规格为准；本篇保留需求和方向，不随实现逐条更新。

## 问题与目标

Haytham Core（HC）和 Gebinde 的消费者需要一个可嵌入的独立运行环境，省去重复编写模块加载、依赖协调、事件执行、任务跟踪和资源收尾的代码。此前讨论过早围绕 Generic Host 与 MessagePipe 展开，又把 Launcher／CLI 的安全退出策略混入 Runtime 的生命周期，导致库选型与实际需求错位。

本篇记录 2026-10-30 讨论已经对齐的分层方向，并给出可继续修改的生命周期概览。用户已确认以此形成草稿；具体接口、状态名和调度细则不是已完成的实现或全部定案的契约。本篇在 docs 中继续修改和定稿，不代表已经完成运行时实现。

2026-10-31 最新澄清：一个进程只允许一个 RuntimeHost；启动器与 CLI 分属不同进程。采用编译期生成模块清单、运行时自动组装，消费者不逐个创建模块。无参数 RuntimeModule 特性标记模块主类；2026-11-01 起，模块的 Id、版本、作者和说明改为来自模块项目的 csproj，不再手写静态 Descriptor（见[模块清单与 NativeAOT](module-entry-aot.md)）。Runtime 先登记内置 OnRegistering、TaskEvent，再接好模块订阅、锁定模块名单；OnRegistering 收集 Registry，校验合并后第二次锁定。TaskEvent 与模块 Event 使用同一机制，每次 Task 执行具有独立信道。

## 分层与生命周期

### 已确认的方向与本篇边界

- HaythamRuntime 提供独立、可嵌入的 Runtime 宿主，由它宏观组织模块与受托管工作的生命周期。消费者不必重新实现这套基础设施。
- HC 和 Gebinde 的模块通过编译期清单接入同一个运行环境；清单的导出与收集方式已确定，生成器已经实现。两库仍互不引用，Runtime 不认识产品业务。给其他语言预先编译 hc、gebinde、full 三种原生库的计划已暂缓，目前只有 Launcher 通过自己的 C# 后端使用 Runtime，见[模块清单与 NativeAOT](module-entry-aot.md)第 1 节。
- 模块注册生命周期挂载点、发布业务事件，并提供挂载点内可调用的完整业务能力。调用方声明业务意图，不重新实现下载、安装等标准算法，也不逐项转发所有库方法。
- 模块订阅 OnRegistering，提交含 Task 触发契约、行为与返回，以及模块 Event 定义和绑定的 Registry，由 Runtime 校验合并。Registry 和事件框架的接口见 [Event 框架规格](event-framework.md)。
- Runtime 通过同一 Event 机制提供并注册 TaskEvent，任务池管理每次 Task 执行；每次执行的 TaskEvent 信道、内部短程工作、取消状态和结果各有归属，不互相混用。
- 对应业务初始化只在实际注册的对应事件执行时发生；模块构造、注入及登记定义本身不自动初始化业务，不要求每个模块都有初始化事件或统一强制回调。
- 调用方后端选择能力并通过挂载点组装产品业务，接收前端触发输入；前端提交操作并展示状态、结果和错误。
- 主生命周期严格串行推进；内部事件和工作可以按各自契约异步、并行或使用多线程。串行阶段不等于固定物理线程，事件不同也不等于执行线程不同。
- Stop 在 Unload 之前可以取消。Launcher／CLI 的安全退出、用户确认和直接退出策略属于应用层，不能原样当作 Runtime 的阶段要求。
- 日志是排错所需的基础能力。库比较必须在提供同等 DI、日志与执行语义的前提下进行，不能把日志需求直接等同于某个宿主库选型。
- 先明确运行契约，再比较基础设施库。Generic Host + MessagePipe 的原选型重新开放评估；本篇没有选定替代库，也没有决定全部手写。

下面的阶段划分是需求草图；精确状态转换、停止投票、订阅快照和调度算法留到契约细化时确定。

### 五层参与方

| 层次 | 负责的事情 | 不应交错的责任 |
|---|---|---|
| Runtime | 宿主阶段、模块依赖与就绪、事件执行、任务及子任务跟踪、持续工作、取消与资源收尾。 | 不理解 Store、Manifest 或 Minecraft 业务，不决定用户安装什么。 |
| HC／Gebinde 总体入口 | 提供可聚合的模块清单、能力和默认创建规则。 | 不让消费者逐个创建和关闭内部对象；模块选择范围需由清单协议明确。 |
| HC／Gebinde 模块 | 实现业务能力，声明就绪条件，注册挂载点，发布业务事件，管理自己的资源操作。 | 不另建一套绕开 Runtime 的通用运行环境，不释放借用的资源。 |
| 调用方后端 | 组装模块和跨库转接，在挂载点补充产品规则，将前端输入转成明确业务请求，将结果和进度桥接回前端。 | 不重写标准业务算法，也不手动编排每个模块的加载、等待和卸载。 |
| 调用方前端 | 收集操作输入，展示进度、状态和错误，提供产品需要的确认与取消交互。 | 不维护后端模块依赖图，不直接承担运行时资源收尾。 |

Gebinde CLI 和第三方消费者可以没有图形前端，但仍使用同样的运行与业务接入契约。现有纯领域能力、Store 工厂和直接消费路径继续保留；使用 Runtime 的场景享有完整托管能力。

以 Minecraft／Forge／KJS 类比：Runtime 类似承载功能的加载与执行环境；库总体入口类似 Mod 入口；模块类似具体功能系统；调用方后端类似整合包规则及 KJS 挂载逻辑。这个类比只帮助理解职责，不要求复制 MC 的静态全局状态、Tick 循环或线程模型。

### 第一类：Runtime 整体生命周期

```text
确保进程唯一 RuntimeHost → 建立最小 Event 能力
  → 直接登记内置 OnRegistering、TaskEvent
  → 读取生成清单、创建模块并接好 OnRegistering 订阅 → 锁定模块名单
  → 执行 OnRegistering → 等待订阅者提交 Registry → 校验合并 Task／Event
  → 两类注册完成，锁定结果
  → 加载 → 启动 → 运行
  → 请求 Stop
      ├─ 被否决 → 继续运行
      └─ 被接受 → 停止执行 → Unload → 已结束
```

| 阶段 | 工作与完成条件 |
|---|---|
| 创建 | 保证进程唯一实例，接入配置与日志；重复入口行为待定。 |
| 引导与模块接入 | 建立最小 Event 能力并直接登记内置 OnRegistering、TaskEvent；读取生成清单、校验描述与构造条件、创建模块并接线，然后锁定名单。 |
| Task／Event 注册 | 执行 OnRegistering，等待订阅者提交 Registry，校验合并两类定义与绑定，拒绝冲突及覆盖内置事件，然后锁定注册结果。 |
| 加载 | 注册结果锁定后按依赖推进；业务初始化仅在实际注册的对应事件执行时发生，完成该事件要求等待的工作。 |
| 启动 | 让已加载模块进入可执行状态，启动所需的持续工作；启动完成不要求持续工作已经结束。 |
| 运行 | 外部输入匹配 Task，由任务池管理本次执行，通过独立 TaskEvent 信道组织内部短程工作并返回结果；模块 Event 使用相同执行机制。 |
| 请求 Stop | 先关闭新外部输入准入，再执行 OnStopRequested；否决则返回被否决并恢复准入。 |
| 停止执行 | 未否决则等已接纳短程 Task 及必要内部工作自然完成，再进入不可逆 OnStopping，结束持续工作并等待真实结束。 |
| Unload | 按实际成功加载顺序反序卸载，只释放自有资源；全部完成则 Stopped，清理失败保留错误并继续仍安全的清理，最终 Hanging 并返回失败。 |

上述注册、运行与正常停止顺序已获用户确认。外部准入关闭不阻断已接纳 Task 的必要内部工作；Task 失败回传原调用方并解除登记，不阻断 Stop。持续工作分开追踪，不能在发送停止信号前等待无限循环。OnStopRequested 处理器自身抛异常的策略及多个处理器的具体判定调度仍待定，不将业务 Task 失败策略直接套用到停止判定。

主阶段推进必须等待该阶段必需的工作。启动中途失败不能自动进入运行；清理出错也不能报告成功卸载。失败时的可用范围、结果结构与回收路径需要明确设计，不在成功主线图中伪装成普通下一阶段。

Runtime 的停止与卸载不等于退出消费者进程，也不等于结束已启动的游戏进程。应用决定何时提出停止、如何与用户交互；Runtime 负责内部执行和真实结果。强杀、断电等情况下的恢复仍由存储设计保证，不能依赖 Stop 回调。

已确认的 Kill 旁路：运行中、Stop 等待中或 Hanging 时，调用方明确选择强制终止，跳过否决、等待与卸载，执行约定终止策略；不自动升级，也不宣称安全卸载。终止宿主进程会结束其中所有工作；进程唯一 Runtime 也不能保证可靠强杀任意托管线程。具体策略接口待定。

### 第二类：模块生命周期

```text
已注册 → 加载中 → 已加载 → 启动中 → 可用 → 停止中 → 卸载中 → 已卸载
```

模块还须表达初始化或执行失败；并非所有模块都有资源，也不要求每个模块实现所有回调。整体阶段串行推进，阶段内模块是否并行取决于依赖与能力契约。

正式规定一模块包一模块主类，模块包之间的 NuGet 依赖代表初始化依赖；普通工具包无模块，不进加载图。NuGet 负责解析版本；模块包构建时由生成器从编译引用中记下依赖的其他模块，应用构建时合并排序，重复 Id、缺少依赖和成环在构建时报错。Runtime 等依赖加载成功才加载依赖方，按实际成功加载顺序反序卸载。不再手写 ModuleDependency。构造参数从能力表按类型取，规则见[模块清单与 NativeAOT](module-entry-aot.md)第 5 节。

- B 依赖 A 的能力，B 必须等待 A 达到所需状态；不能靠订阅顺序猜测就绪。
- 无依赖的模块可以并行初始化。卸载时先结束资源使用方，再释放资源提供方。
- 某模块失败时，受影响依赖不能无限等待，也不能继续使用失效能力；无依赖模块是否继续提供服务需要明确故障范围。
- 模块完成一次业务任务不等于模块卸载。统一注册也不代表所有能力必须同时就绪。

例如 HC Store 提供能力，跨库转接将同一实例绑定为 Gebinde 声明的接口；Runtime 管理依赖关系，转接只借用，不取得关闭权。运行时提供公共协调机制，Store 的实际打开与释放由业务模块实现。

### 第三类：挂载点与事件执行生命周期

Event 可以组织执行、等待与完成，订阅者实现业务。模块 Event 继承基元 Event，Runtime 在其中管理每次执行的生命周期；这不是仅广播状态的通知表。具体载入点与订阅接口仍需细化，下面列的是执行用途，不是一棵已确定的继承树。

```text
触发 → 确定参与者 → 按事件契约执行 → 等待必要工作 → 返回结果或错误
```

与 Tick、玩家右键等事件的类比是：不同事件有不同触发时机、顺序、等待和取消规则。这个类比不意味着这些 MC 事件天然运行在不同线程，也不要求 Runtime 内置游戏 Tick。

| 用途 | 建议的执行约束 |
|---|---|
| 修改共同参数或依次加工方案 | 显式串行，确定顺序和修改权限。 |
| 相互独立的初始化处理或观察者 | 可以并行；属于阶段完成条件的处理器必须被等待。 |
| 判断是否允许 Stop | 明确汇总允许／否决结果，再决定是否推进。 |
| TaskEvent 承载下载等 Task | Runtime 自己注册的 Event；每次执行有独立信道和明确结果，不能因为增加观察者而重复执行业务。 |
| 进度与状态通知 | 可供多个观察者订阅；缓冲、节流、顺序与慢订阅者规则按事件用途细化。 |
| 清理挂载点 | 尽力完成仍然有效的清理义务，保留原始故障和后续清理错误。 |

事件处理器可执行业务，不仅限于观察。处理器须等待自己的必要工作，或通过 Runtime 登记到明确的阶段／任务作用域；不能启动不可追踪的后台工作后宣称阶段完成。脱离当前阶段的持续工作必须有新的明确归属。

Stop 否决、取消任务和停止事件继续传播是三个独立语义。订阅优先级不能代替模块依赖；解除订阅也不代表已经执行的处理器结束。当前派发参与名单、重入与退订效果在接口设计时确定，不提前把全局串行和永久稳定订阅顺序设为所有事件的要求。

### 第四类：单次业务任务生命周期

下载、纳入、修复、清理等是模块注册的 Task 定义，声明收到什么触发、执行什么、返回什么。一次定义可执行多次；这里的领域 Task 不等于 `System.Threading.Tasks.Task`，代码命名另行确定。

```text
外部输入 → 匹配已注册 Task 并检查准入
  → 建立执行记录，纳入任务池 → 建立本次专属 TaskEvent 信道
  → 按注册规则执行订阅者，内部短程工作在信道内执行与等待
  → 必要工作实际结束 → 成功／失败／已取消
  → 返回调用方，完成在途登记并回收本次信道
```

TaskEvent 使用与模块 Event 相同的机制。每次执行的数据、取消状态与结果归属隔离；内部一次性短程工作留在本次信道内。隔离不自动解决共享文件或对象的竞争。任务池不意味着每个 Task 都有独立线程，其并发与调度规则待定。

这是已确认的语义流程，具体回传、解除登记和回收信道的底层时序仍需设计；不能在必要工作未结束时伪造终态。

```text
已提交 → 等待执行 → 执行中 → 成功 / 失败 / 已取消
```

取消是请求，终态表示工作实际结束，两者不能混为一谈。Runtime 提供任务身份、状态和结果、父子归属、取消与等待、调度及并发限制、进度传递和资源作用域。业务模块提供实际算法及业务一致性约束。

父任务完成必须考虑其必需子任务；失败和取消也必须能追踪到相关工作。后续设计需要防止父任务占满执行名额后等待无法启动的子任务，以及生命周期回调等待依赖该回调完成才能就绪的能力等死锁。

异步不会自动带来幂等性。重复生命周期调用、重复任务提交、网络重试和重复业务操作分别规定：Runtime 可以管理调用状态，安装或写入的业务幂等仍由模块负责。是否合并重复调用尚未定案，不能默认重试。

### 第五类：持续工作与执行资源生命周期

```text
注册 → 启动 → 持续运行 → 收到停止信号 → 实际结束
```

队列消费者、监测循环等工作需要明确所属模块或作用域。Runtime 跟踪其启动、失败和结束，避免生命周期之外遗留工作。持续工作运行期间产生的业务任务仍有自己的任务生命周期。

实现可以使用异步 I/O、线程池或有确切需要的专用线程。一个 Runtime、模块或任务不自动对应一条操作系统线程。是否需要主执行线程、线程亲和性、专用调度器及并发分组，在具体执行契约与负载验证时确定。

### 横跨各层的约束

- 进程唯一性与归属：同进程不得创建第二个 RuntimeHost，重复调用政策待定；可变状态、订阅和工作归属由该实例管理，不散落在进程级静态总线中。独立进程各有自己的实例。
- 资源所有权：Runtime 组织清理，模块释放自己拥有的资源，借用方不释放提供方资源；事件通道须覆盖必要的结束通知。
- 显式失败：沿用[错误与兜底规则](development.md#错误与清理)。日志不能代替错误传播，不用吞错或默认值伪装健康运行；清理继续执行不等于业务失败后继续执行正常流程。
- 日志：能关联 Runtime、模块、阶段和任务，输出接入由消费者配置；遵守[机密不外泄](development.md#日志与机密)，不记录凭据或游戏命令行。
- 嵌入与公开消费：框架不反向引用 HC／Gebinde，公开依赖不能落在 Launcher 私有实现；DI 仍在组装入口使用，不变成业务处理器中的服务定位器。
- NativeAOT 与 FFI：继续以实际发布验证裁剪及动态代码路径；内部事件不直接成为 C ABI，跨 Dart 边界继续使用既有 op、job 和事件 port。

### 一个贯穿分层的业务例子

1. 调用方引用所需模块包，配置跨库能力、日志和环境；构建生成聚合清单，Runtime 自动组装模块。
2. Runtime 先登记内置事件、接好 OnRegistering 订阅，再锁定模块名单，执行 OnRegistering 收集 Registry；校验合并并锁定结果后，按实际生命周期依赖加载与启动。
3. 前端提交安装整合包的位置和选项，后端转换为明确安装请求。
4. Runtime 匹配安装 Task，为本次执行建立独立 TaskEvent 信道。Gebinde 的订阅者执行业务，在挂载点接受产品规则；需要 HC 能力时通过转接使用。
5. 本次内部短程工作在其信道内流转，Runtime 通过任务池和统一 Event 机制管理执行、等待与取消。后端将本次进度与结果桥接给前端。
6. 应用提出 Stop 时，Runtime 执行可取消挂载点；获准后再按契约结束工作并 Unload。界面确认和进程退出决策仍由应用负责。

### 后续细化与文档维护

实施顺序以[手写教程总纲](runtime-authoring-roadmap.md)为准：先建立 RuntimeHost 状态外壳并明确进程唯一性，再接入静态模块描述、资格标记、生成清单、自动组装、Event 执行基础和 OnRegistering／Registry，两次锁定后接通加载启动；随后完善 TaskEvent 信道、停止与卸载。运行实例不等于专用线程，状态外壳不允许跳过事件初始化。保留用户笔记；清单协议、创建规则、注册 API 与包布局仍待具体设计，基本失败处理随功能首次实现同步补入。

本篇是 HaythamRuntime 仓库的需求与生命周期工作稿，由根目录 README 链接。后续 Runtime 设计在本仓库继续修订；Launcher 仓库保留迁入时的讨论材料与产品集成记录。文档定稿不代表代码实现。

## 考虑过的其他做法

- **继续以 Generic Host + MessagePipe 为固定前提细化需求。** 优点是已有候选与 POC 可复用；当前不锁定，因为需要先纠正应用退出与嵌入执行环境的需求错位。二者仍可参加后续比较，Generic Host 也不应被简单称为进程管理器。
- **Runtime 只提供事件工具，协调逻辑全部交给消费者。** 优点是公共库实现小、应用控制自由；不采用，因为消费者仍须重建模块、任务和资源生命周期，违背节省接入代码的目标。
- **所有工作统一在一条线程串行执行。** 优点是局部顺序直观；不作为统一要求，因为下载、初始化和独立任务需要异步与并发。保留主生命周期串行，为具体事件定义调度契约。
- **所有事件一律广播或一律使用同一调度方式。** 优点是表面 API 简单；不采用，因为请求、策略修改、通知、停止否决和清理的结果与等待要求不同。
- **完全手写或采用其他事件／执行库组合。** 可以精确匹配语义或减少内核维护；两者仍为候选，需按同等需求比较后决定，不能以旧 POC 的代码行数直接定案。

## 验收目标

以下是生命周期行为的验证目标。其中主线、停止否决、启动回滚、持续工作重试和 Kill 已经由 `dotnet test` 运行的验证场景检查过；日志、清理错误汇总、DI 和候选实现比较还没有验证。

- 消费者通过统一入口自动接入生成清单中的模块，不逐个创建或卸载；同进程重复／并发创建不得产生第二个 RuntimeHost，独立进程可以分别运行。
- 两次锁定的窗口明确：模块名单锁定后仍能通过注册事件登记 Task／Event，两类注册完成后才锁定结果；注册失败不进入运行。
- TaskEvent 与模块 Event 使用同一机制；同一定义的两次 Task 执行信道、状态、取消和结果不混用，内部短程工作不会脱离本次归属。
- 主阶段不重叠推进；阶段内允许独立工作并行，所有必要工作完成后才进入下一阶段，持续工作具有独立归属。
- 依赖能力未就绪时不会提前使用，初始化失败明确影响依赖方，并组织已经创建资源的清理。
- Stop 被否决时没有进入 Unload，环境能按契约继续运行；接受停止后，工作准入、等待与资源释放顺序一致，不提前报告结束。
- 异步挂载点及登记子任务被正确等待，任务取消与真正完成可区分；覆盖父子任务调度、重入及就绪等待的死锁边界。
- 请求有明确执行责任和结果；增加进度观察者不重复执行业务。频繁订阅退订与任务结束后不无限保留历史对象。
- 清理失败仍暴露原始错误并完成其他必要清理；日志可定位阶段和任务且不泄露机密。
- 候选实现接受同等 DI、日志和任务负载比较；实际 NativeAOT 发布通过现有警告要求，嵌入不擅自接管进程退出。
- 文档中的本地链接有效，状态和实现一致；不能将文档校验当成生命周期或 NativeAOT 验证。

## 风险与代价

- 集中管理生命周期能减少消费者接线，但运行时必须维护真实的依赖、工作归属和资源有效期，不能只做事件转发外壳。
- 阶段串行不自动保证线程安全或幂等；并行处理器若共同修改状态，需要明确顺序或隔离。性能收益需要测量，不能从结构直接推断。
- 停止否决若发生在不可逆清理之后，会导致半关闭状态；停止投票与任务取消必须分清。
- 未登记工作、无限运行的处理器和不响应取消的操作会阻碍收尾；超时不能被描述为线程已终止或资源已安全释放。
- 过早固定全局顺序、专用线程或完整插件加载器会扩大公共契约。反过来，若把这些基础设施全部留给消费者，也会丢失 Runtime 的实际价值。
