# 任务并发上限

## 要解决的问题

用户同时对几个实例发起安装，又在跑清理扫描时，同时展开的任务数量不受控制。第一版不设上限：同一个排队键的任务依次执行，不同键的任务直接同时执行。

## 目前的想法

- 提供配置入口，默认不设上限。配置从配置文件读取后，在组装 Runtime 时注入。
- 根任务并发和子任务并发分别有一个配置项。
- 上限主要针对用户手动发起的任务（主动并发）。后台任务（被动并发）要和它分开考虑，见[后台任务的加权调度](weighted-background-scheduling.md)。
- 在等排队键的任务不占名额，免得一堆同实例的任务占满名额却都在等。
- 子调用不重新排进根任务的队列，也不和父任务争根名额。例如安装任务调用 Storage 的保存任务并等待它，如果保存任务要重新排队，就会排在安装后面，而安装正在等它。
- 上限只表示“同时执行多少个任务”，不等于下载连接数或线程数。下载器自己的连接数限制仍由下载器管理。

## 还没想清楚的地方

子任务的上限怎样计数。例如子任务上限是 4，四个子任务都在跑，每个又调用了一个孙任务并等待它；如果孙任务也要等子任务名额，就永远等不到。所以要先定下来：

- 子任务上限按每个根任务计算，还是全局计算。
- 正在等待自己后代的子任务，算不算占用名额。

这部分要先交给 Astra 设计，再实现。

## 为什么现在不做

第一版没有已经确认的负载问题，HL 的调度讨论纪要（2026-10-26）也还标着“未批准”。Astra 在评审文件第九轮给过一版根任务上限的规则和签名（`RuntimeSchedulingOptions(MaxConcurrentRootTasks)`），可以作为起点。
